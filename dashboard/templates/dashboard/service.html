{% if service.key == 'acm' %}
About Floci ACM

Local ACM stores AWS-compatible certificate metadata and issues requested certificates immediately for local emulation.

ACM is most often used to test TLS certificate wiring for load balancers, CloudFront, API endpoints, and infrastructure automation. In Floci, a good learning flow is to request a certificate, inspect the issued metadata and validation options, add tags, then export a private certificate when testing workflows that need key material.

Certificates use real RSA or EC keys and valid X.509 structure. Validation is emulator-friendly, and only PRIVATE certificates can be exported with an encrypted private key.

{% elif service.key == 's3' %}
About Floci S3

S3 is the object storage layer for local AWS work: buckets hold durable objects, keys give those objects names, metadata and tags describe them, and URLs or SDK calls move bytes in and out. Floci S3 gives you a fast local place to build that storage model before your app points at AWS.

  1. Start with a bucket. Create a bucket for one app or workflow, then select it in the browser to inspect object counts, versioning state, encryption settings, tags, and policy-related configuration.
  2. Upload a real object. Use the workbench upload flow to send a small file or JSON payload. Open the object detail drawer to confirm the key, size, ETag, content type, metadata, tags, and last-modified time your app will later depend on.
  3. Practice key design. Organize objects with folder-style prefixes such as uploads/, exports/, or customers/123/. Prefixes are just key names, so test list, copy, rename-style copy/delete, and delete behavior with the same shapes your app uses.
  4. Test access patterns. Download objects, overwrite them, copy them, generate presigned URLs, and try missing-bucket or missing-key cases. These are the paths most apps hit in normal use and during cleanup or retry logic.
  5. Add storage controls intentionally. Turn on versioning, default encryption, CORS, lifecycle rules, bucket policies, object tags, and metadata when the workflow needs them. Use the read-only inventory below the workbench to confirm Floci stored the configuration you expected.
  6. Clean up like production code would. Empty buckets before deleting them, remove test prefixes after a workflow, and verify your app handles empty lists, duplicate uploads, overwritten objects, and object-not-found responses cleanly.

The S3 labs turn this into a guided sequence: create a bucket, upload and retrieve objects, organize prefixes, work with metadata and tags, recover versions, generate presigned URLs, configure security and encryption, set lifecycle and CORS rules, send S3 notifications to SQS, and complete a multipart upload. Use this workbench when you want to explore freely; use the labs when you want the shortest proven path through the concepts.

Useful local test cases include upload and download paths, overwrite behavior, empty bucket cleanup, versioning changes, object tagging, copy operations, prefix browsing, presigned URL flows, and app behavior when a bucket or object does not exist. Bucket policy and ACL authorization is optional: set FLOCI_SERVICES_S3_ENFORCE_AUTH=true to enforce public/private reads and reject unknown signed access keys. Replication execution, access logging, and inventory are not available. Floci 1.5.32 also returns the AWS-compatible default SSE-S3 configuration for buckets without an explicit encryption rule.

{% elif service.key == 'iam' %}
About Floci IAM

IAM is the control layer for local AWS work: it answers who is making a request, which credentials they are using, and whether a policy allows the action. Floci IAM gives you a safe local place to build that model before you wire it into an app.

  1. Start with principals. Use the tabs to inspect users, groups, roles, managed policies, and instance profiles. Select any principal to see its ARN, attached policies, inline policies, access keys, trust policy, or group membership.
  2. Create the admin identity first. A fresh Floci account starts with bootstrap root-like credentials. Use them the way you would use AWS root: only long enough to create an administrator user, attach administrator permissions, create an access key, and switch daily work to that admin identity.
  3. Create other identities intentionally. Create users for people or app credentials, groups for shared user permissions, roles for temporary credentials, and instance profiles when EC2-style workloads need a role.
  4. Attach permissions in small pieces. Managed policies are reusable and versioned. Inline policies live directly on one user, group, or role. In Floci, a good first policy is a narrow allow such as s3:ListAllMyBuckets or sqs:ListQueues, then broaden only when the workflow needs it.
  5. Separate role trust from role permissions. A role needs a trust policy that says who may assume it, and a permissions policy that says what the resulting temporary credentials may do. Use the role trust templates for Lambda, EC2, account-root testing, or custom JSON.
  6. Test the identity, not just the policy document. Use Use this user to switch the dashboard session to a user, or Get temporary credentials to assume a role. Then try the target service from Floci, the workbench, or the AWS CLI Console and confirm both the allowed path and the denied path.
  7. Clean up after experiments. The cleanup buttons remove lab-style dependencies such as keys, group membership, attached policies, inline policies, and role/profile links before deleting the principal.

The IAM labs turn this into a guided sequence: create a local admin user first, create regular users, attach managed and inline policies, use access keys, work with groups, create roles, constrain STS sessions, wire instance profiles, and verify real IAM enforcement with switched identities. Use this workbench when you want to explore freely; use the labs when you want the shortest proven path through the concepts.

Useful local test cases include missing permissions, explicit deny behavior, incorrect trust policies, inactive access keys, group policy inheritance, session-policy constraints, permission boundaries, and role-session credential wiring. Floci 1.5.29 routes assumed-role credentials to the target account.

{% elif service.key == 'sqs' %}
About Floci SQS

Local SQS emulator for queue-driven workflows. Polling messages makes them temporarily invisible until the visibility timeout expires or they are deleted. Floci 1.5.25 aligns MaximumMessageSize with AWS at 1 MB and reports delayed-message counts in queue attributes.

SQS is most often used to decouple producers from background workers, smooth traffic spikes, retry failed work, and connect services without requiring them to run at the same time. In Floci, a good learning flow is to create a queue, send a test message, poll it from the UI, inspect the body and attributes, then delete it after your worker logic succeeds.

Common local test cases include producer message format, consumer retry behavior, visibility timeout handling, delete-after-success behavior, purge cleanup, FIFO ordering, duplicate handling, and dead-letter queue flows.

{% elif service.key == 'ec2' %}
About Floci EC2

Local EC2 can launch Docker-backed instances, manage lifecycle state, inject imported SSH public keys, run UserData, and expose IMDS-compatible metadata for local compute workflows.

EC2 is most often used to test software that expects an instance-like runtime, VPC placement, security group metadata, or IAM instance profile credentials. Start from Overview, launch an instance from a built-in AMI, inspect its network placement and tags, then follow lifecycle state from the Instances view.

Use Run Command for AWS-native shell execution through Systems Manager. Floci executes AWS-RunShellScript asynchronously inside a running Docker-backed instance and returns standard output, standard error, and exit status without giving the dashboard direct Docker access.

The Network view maps VPCs to subnets, instances, internet gateways, route tables, NAT gateways, and VPC endpoints. Connectivity diagnostics call out missing edge paths, missing associations, empty inbound policies, unassociated Elastic IPs, and resources that still reference a deleted VPC.

The Security view manages security groups and their inbound and outbound rules. CIDR-sourced TCP ingress rules are especially useful locally because Floci publishes eligible application ports through forwarding sidecars.

The Advanced view covers network ACL entries and subnet association moves, S3-delivered VPC flow logs with decoded record viewing, EBS-style volumes and snapshot inventory, registered AMIs, versioned launch templates, and one-time Spot requests. Snapshot creation/deletion and AMI deregistration are not currently exposed by Floci, so those inventories remain intentionally non-destructive.

Common local test cases include UserData bootstrapping, IMDSv1 and IMDSv2 calls, IAM instance profile credential wiring, SSM commands, tag-based discovery, VPC routing, endpoint placement, security group ingress, and app behavior across stop/start or termination.

{% elif service.key == 'rds' %}

{% elif service.key == 'backup' %}

Local AWS Backup stores backup vaults, plans, selections, simulated backup jobs, recovery points, protected resources, and tags through the AWS-compatible REST JSON API.

{% elif service.key == 'textract' %}

{% elif service.key == 'transcribe' %}

{% elif service.key == 'bedrockruntime' %}

{% elif service.key == 'scheduler' %}
About Floci EventBridge Scheduler

Local EventBridge Scheduler stores schedule groups and schedules through the AWS-compatible REST JSON API. When invocation is enabled, a local dispatcher fires due schedules on a short polling interval.

Scheduler is most often used to trigger Lambda functions, send SQS or SNS messages, or put EventBridge events on a recurring or one-time cadence. In Floci, a good learning flow is to create a group, add a rate or at expression, point the target at a local service, then watch the target service workbench for the fired payload.

Supported expressions include at, rate, and six-field cron. Retry policy and dead-letter config are stored for compatibility, but failed-invocation retry behavior is not enforced yet.
